1. Vision & problem statement

Vision: a single system of record for a drilling site's equipment and crew operations, usable offline from the field, so every reading, shift report, maintenance action and part movement is captured once, correctly, and visible to the people who need it.

Problem: field data (pre-start checks, shift production, faults) is currently captured on paper or ad hoc spreadsheets, maintenance is tracked informally, and management reporting requires manually reconciling numbers from multiple sources. This causes delayed fault response, missed maintenance intervals, inventory stockouts, and reporting that lags the actual state of the site by days.

3. Goals & non-goals

Goals

  • Replace paper daily-reading and shift-report sheets with a mobile form that works with no signal
  • Automate maintenance due-tracking from real hour-meter data, not memory
  • Tie parts consumption to job cards so stock levels stay accurate
  • Give managers on-demand and scheduled reports without manual reconciliation
  • Enforce accountability: every submission is attributable, every approval is audited

Non-goals (current phase)

  • Predictive/ML-based maintenance forecasting
  • Financial/procurement system integration beyond purchase-request tracking
  • Real-time equipment telemetry / IoT sensor ingestion
  • Multi-tenant SaaS packaging (currently single-organization, multi-site)

4. Feature epics

4.1 Authentication & device management

Employee-ID + password login, TOTP 2FA required for managers/admins, rotating refresh tokens, optional device pre-approval so a new phone can't sign in until an admin approves it, forced password change on first login.

4.2 Asset register

Site-scoped registry of drilling, haulage, compressor and ancillary equipment with an immutable asset number, assigned operator(s), and a status that automatically reflects open maintenance work.

4.3 Daily equipment readings

Per-asset, per-day pre-start check: hour meter, fuel, fluid levels, tyre pressures, warning lights/noises/leaks, condition rating, photo/signature — submitted from the field, one per asset per day, auto-flagging alerts on faults.

4.4 Shift production reporting

Drilling shift report: hole reference, depth range (server-computed meters drilled), holes completed, rock type, penetration rate, downtime, and chemicals consumed against a master chemical list with cost tracking. Goes through submit → approve → (optional) unlock-for-correction.

4.5 Maintenance scheduling

Per-asset schedules driven by hour-meter interval, calendar interval, or condition; automatic status (upcoming/due/overdue) computed daily; reminder notifications to assigned technicians and supervisors; weekly digest to managers.

4.6 Job cards & parts

Work orders for scheduled service, breakdown repair, modification or inspection, with auto-generated job numbers, technician sign-off, and a parts-used list that deducts from inventory transactionally and triggers low-stock notifications.

4.7 Parts inventory & purchasing

Stock levels with a full movement audit trail, minimum-quantity thresholds, and a purchase-request workflow (open → ordered → received) for replenishment.

4.8 Notifications

In-app notification centre plus mobile push (FCM), covering maintenance due/overdue, approval requests, job card approvals, machine alerts, report-ready, and low-stock events, targeted by role and site.

4.9 Reporting

Seven report types (production, utilisation, maintenance summary, job card history, chemical usage, asset health, employee activity), each role-gated, exportable as PDF and XLSX, shareable by email, generated on demand or automatically at month-end, archived for 24 months.

4.10 Offline sync

The mobile app queues all writes locally and replays them once connectivity returns; the server treats replays idempotently and routes genuine conflicts (e.g. two people editing the same day's reading) to a supervisor review queue rather than silently overwriting data.

6. Release status

Per docs/DEVELOPMENT_PLAN.md §13 (as of 2026-08-21), all ten planned phases are implemented: foundation/auth incl. 2FA, asset register, daily readings + alerts, shift production + approval/unlock, offline outbox sync, maintenance schedules + reminders, job cards + parts + asset-status automation, parts inventory + purchase requests + push + notification centres, the 7-report suite with PDF/XLSX/email/month-end cron, and release hardening (device registration, integration tests in CI, k6 load test, production config guards, Android release signing, demo data, README runbook).

Known gaps carried forward: mobile push requires a manual post-clone step to add Firebase config files and the @react-native-firebase/messaging dependency (server-side FCM sending is fully implemented); no production Dockerfiles exist yet for the API or web app; the web app has no automated test suite.

7. Risks & open questions

  • Connectivity risk: field sites may have long offline windows — the outbox is FIFO and caps batches at 50-200 ops per flush; very long offline periods should be validated against real-world queue sizes.
  • Conflict resolution UX: sync conflicts currently require manual supervisor review; if conflict volume grows, this queue needs monitoring.
  • Redis is provisioned but unused by the current API (cron runs in-process) — decide whether to formally drop it from infra or adopt it for a job queue as the plan originally intended.
  • Containerized deployment for API/web is not yet defined in-repo; needed before a production rollout beyond the documented manual runbook.
