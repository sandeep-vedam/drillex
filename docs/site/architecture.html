System topology

Both the mobile app and web console talk only to the API over HTTPS/REST — neither has a direct database or storage connection. All three clients share the same validation rules and permission matrix from packages/shared, so a rule is written once and enforced identically everywhere.

Monorepo layout

drillex/
├── apps/
│   ├── api/           NestJS backend — REST API, Prisma, cron jobs
│   ├── web/            Next.js 15 — supervisor/manager dashboard + admin console
│   └── mobile/         React Native (bare CLI) — field app for operators/technicians
├── packages/
│   └── shared/          @drillex/shared — Zod schemas, enums, RBAC matrix, calc helpers
├── infra/
│   ├── setup-vps.sh         One-time VPS provisioning (Node 20, MySQL 8, nginx)
│   └── load/k6-smoke.js     k6 load test against SRS §9.5 NFR targets
├── docs/
│   ├── DEVELOPMENT_PLAN.md  original build plan + status log
│   └── site/                 this documentation set
└── .github/workflows/ci.yml  install → migrate → seed → typecheck → test → build

Package manager: pnpm workspaces (apps/*, packages/*), task orchestration via Turborepo. Node ≥20 at the repo root; the mobile app requires Node ≥22.11.

Plan vs. implementation The original plan proposed Expo + WatermelonDB for mobile and additional packages/ui / packages/config workspaces. The shipped app uses bare React Native CLI with a custom AsyncStorage-backed outbox instead (documented as a deliberate 2026-08-21 decision — WatermelonDB remains the upgrade path if bidirectional offline editing is ever needed), and only packages/shared exists today.

Authentication & RBAC

Every request passes through three global guards, in order: ThrottlerGuard (rate limiting) → JwtAuthGuard → RbacGuard. Routes are deny-by-default — a route must explicitly declare @RequirePermission(...) to be reachable by anything other than an unauthenticated health check.

Session lifecycle

  • Login: employee ID + Argon2id password check, every attempt logged
  • 2FA (TOTP) enforced for MANAGER/ADMIN before a session is granted
  • Access JWT: 15 min default; Refresh token: 30 days, hashed at rest, rotates on every use
  • Optional device pre-approval gate before login/refresh succeeds

Permission matrix

A single table in packages/shared/src/rbac.ts maps each of 5 roles to a scope per permission:

ScopeMeaning
selfonly records the user owns
siterecords within the user's site
allcross-site (admin-level)

Services translate the resolved scope into a Prisma where filter (e.g. an asset-scope helper), so access control is enforced at the query layer, not just the route layer.

Offline sync

Each queued operation carries a client-generated UUID. The server treats replays as idempotent by that ID: an already-applied op returns duplicate; a validation/permission failure returns rejected with a reason (kept in the mobile Outbox screen for retry); a genuine data conflict (e.g. two submissions for the same asset+date) is written to the SyncConflict table rather than resolved automatically, and surfaced to supervisors on the web Sync Conflicts page for manual review.

Scheduled jobs

JobSchedule (UTC)Purpose
Maintenance remindersDaily 06:00Recompute schedule status, notify technicians/supervisors on due/overdue items (20h de-dupe window)
Maintenance weekly digestMonday 07:00Summary of all due/overdue schedules to all managers
Month-end reports1st of month, 02:00Generate all 7 report types for the prior month, notify managers
Report purgeQuarterly, 1st, 03:00Delete archived reports older than 24 months

All four run in-process via @nestjs/schedule — no external job queue is wired in, and Redis has been dropped from infra accordingly.

Domain automation

  • Parts ↔ job cards: adding parts to a job card runs in a Prisma transaction that creates a stock movement and adjusts qtyOnHand; removing/editing reverses it; crossing below minQty triggers a low-stock notification.
  • Asset status: any job card in OPEN/IN_PROGRESS/AWAITING_PARTS forces the asset to UNDER_MAINTENANCE; when the last one closes, the asset reverts to ACTIVE (unless DECOMMISSIONED).
  • Job numbering: sequential per calendar year, computed transactionally to avoid collisions (JC-2026-0001, …).

Deployment & infra

Local / CI

  • infra/setup-vps.sh + infra/deploy.sh: Node 20, MySQL 8, nginx, PM2 — no containers
  • CI (.github/workflows/ci.yml): install → prisma migrate deploy → seed → typecheck → test → build (API + web only; mobile not built in CI)
  • k6 smoke test validates the §9.5 performance NFRs against a seeded dataset

Production readiness

  • API refuses to boot in production without strong JWT secrets
  • Recommended: STORAGE_DRIVER=s3, real SMTP/FCM credentials, DEVICE_REGISTRATION_REQUIRED=true, TLS termination at the load balancer, managed MySQL with backups
  • Deployment is container-free by design: PM2 runs both Node processes, nginx terminates HTTP, MySQL runs natively
