§1 Scope

This specification covers the API (apps/api), the web console (apps/web) and the mobile field app (apps/mobile) that together make up Drillex Ops, plus the shared validation/permission package (packages/shared). Out of scope: IoT telemetry ingestion, financial/ERP integration, multi-tenant SaaS operation.

§2 Authentication & device management

IDRequirement
FR-2.1The system shall authenticate users by employee ID and password, with passwords hashed using Argon2id.
FR-2.2The system shall record every login attempt (success and failure) with employee ID, device ID, IP, and timestamp.
FR-2.3The system shall require TOTP-based two-factor authentication for MANAGER and ADMIN roles before granting a session.
FR-2.4The system shall issue a short-lived JWT access token (default 15 min) and a rotating opaque refresh token (default 30 days, hashed at rest); each refresh shall revoke the prior token.
FR-2.5The system shall support an optional device-approval mode where an unapproved device cannot complete login or token refresh until an ADMIN approves it.
FR-2.6The system shall support a forced password-change flag that blocks normal use of the API until the user sets a new password.

§3 Asset register

IDRequirement
FR-3.1The system shall allow ADMIN/MANAGER/SUPERVISOR to create, read, update, and soft-delete assets scoped to their site(s).
FR-3.2Each asset shall have an immutable, unique asset number assigned at creation.
FR-3.3The system shall support assigning one or more operators to an asset for a validity period, and shall restrict daily-reading/shift-report submission for that asset to its assigned operator(s).
FR-3.4Asset status (ACTIVE / UNDER_MAINTENANCE / IDLE / DECOMMISSIONED) shall be automatically set to UNDER_MAINTENANCE while any job card on that asset is open, and reverted to ACTIVE when none remain open.

§4 Shift production reporting

IDRequirement
FR-4.1The system shall accept one shift report per asset per date+shift combination, capturing hole reference, start/end depth, holes completed, rock type, penetration rate, downtime hours/reason.
FR-4.2The system shall reject a shift report where end depth is less than start depth, and shall server-compute total meters drilled.
FR-4.3The system shall support recording multiple chemical line items per shift report against a master chemical list, with quantity, unit, purpose, and stock-on-hand.
FR-4.4A shift report shall progress SUBMITTED → APPROVED by a SUPERVISOR or MANAGER; an operator shall not be able to approve their own or any report.
FR-4.5An APPROVED report may be UNLOCKED by an authorized approver with a recorded reason, returning it for correction; the unlock action shall be audited.

§5 Daily equipment readings

IDRequirement
FR-5.1The system shall accept at most one daily reading per asset per calendar date.
FR-5.2A reading shall capture hour meter, fuel start/end (system computes consumption), fluid levels (engine oil, hydraulic oil, coolant), air filter condition, battery condition, tyre pressures, and boolean flags for warning lights / unusual noises / leaks with free-text notes.
FR-5.3The system shall automatically raise an alert when a reading is submitted with a condition rating at or below the configured threshold, or with any fault flag set to true.
FR-5.4The system shall support attaching a photo and/or signature to a reading.

§6 Maintenance scheduling

IDRequirement
FR-6.1The system shall support maintenance schedules per asset keyed by service type (HR_250, HR_500, HR_1000, ANNUAL, CONDITION_BASED, AD_HOC) with an hour-based or day-based interval.
FR-6.2The system shall compute schedule status (UPCOMING / DUE_NOW / OVERDUE) daily, using the latest recorded hour meter for hour-based schedules.
FR-6.3The system shall send reminder notifications to assigned technicians and site supervisors starting at a configurable lead time before due, de-duplicated within a 20-hour window.
FR-6.4The system shall send a weekly digest of all due/overdue schedules to all MANAGER users.
FR-6.5Completing a schedule shall roll a recurring schedule forward to its next cycle, or close a one-off schedule, and shall re-evaluate the asset's status.

§7 Job cards & parts

IDRequirement
FR-7.1The system shall auto-generate a sequential, human-readable job number per calendar year (format JC-YYYY-####) for each job card.
FR-7.2A job card shall record job type (SCHEDULED_SERVICE / BREAKDOWN_REPAIR / MODIFICATION / INSPECTION), reported fault, work performed, hour meter, labour hours, assigned technician(s), before/after condition rating, and test result.
FR-7.3Adding parts to a job card shall transactionally deduct the used quantity from the corresponding part's stock-on-hand and record a stock movement; editing/removing shall reverse the movement.
FR-7.4The system shall notify MANAGER and TECHNICIAN roles when a part's stock-on-hand falls below its configured minimum quantity.
FR-7.5The system shall support a purchase-request workflow per part with states OPEN → ORDERED → RECEIVED (or CANCELLED).
FR-7.6A job card shall require technician sign-off (signature attachment) and, per role policy, supervisor approval before considered complete.

§8 Reporting

IDRequirement
FR-8.1The system shall provide seven report types: Drilling Production, Machine Utilisation, Maintenance Summary, Job Card History, Chemical Usage, Asset Health, and Employee Activity.
FR-8.2Chemical Usage and Employee Activity reports shall be restricted to MANAGER and ADMIN roles.
FR-8.3Each generated report shall be rendered as both PDF and XLSX, stored in object storage, and archived as a Report record for 24 months, after which it is purged by an automated job.
FR-8.4The system shall support emailing a generated report to a specified recipient.
FR-8.5The system shall automatically generate all seven report types for the prior calendar month on the 1st of each month and notify managers when ready.

§9 Cross-cutting requirements & NFRs

§9.1 Role-based access control

IDRequirement
FR-9.1.1The system shall enforce a permission matrix mapping each role to a scope (self / site / all) per resource, applied identically across API, web, and mobile. The matrix is stored in the database and read fresh per request/session — not hardcoded in source — so a grant change takes effect without a redeploy.
FR-9.1.2Every API route shall require authentication and pass an explicit permission check by default (deny-by-default).
FR-9.1.3The system shall allow an ADMIN (via the role:manage permission) to create, rename, and delete roles at runtime, and to edit each role's permission grants, without a code change or deployment. Each role has an immutable key (used internally and in the JWT) distinct from its editable display name, so renaming a role never affects access-control logic keyed off it. The 5 built-in roles seeded on installation (OPERATOR, TECHNICIAN, SUPERVISOR, MANAGER, ADMIN) cannot be deleted; a custom role with users still assigned to it cannot be deleted either.
FR-9.1.4The system shall allow an ADMIN to reassign any user's role after account creation, in addition to setting it at creation time.

§9.2 Offline synchronization

IDRequirement
FR-9.2.1The mobile app shall queue writes locally when offline and flush them to the server automatically on reconnect and on a periodic interval.
FR-9.2.2The server shall process synced operations idempotently by client-generated operation ID; a replayed operation shall be reported as a duplicate, not reapplied.
FR-9.2.3A synced operation that would violate a uniqueness constraint already satisfied by another source shall be routed to a conflict queue for manual supervisor resolution rather than silently overwritten or dropped.

§9.3 Audit

IDRequirement
FR-9.3.1Every create, update, delete, approve, complete, and resolve action shall write an audit log entry capturing actor, device, entity, action, and a diff of the change.

§9.4 Notifications

IDRequirement
FR-9.4.1The system shall deliver notifications both in-app (persisted, markable read) and via mobile push, targetable by role and site.

§9.5 Non-functional requirements

IDRequirement
NFR-PERF-1Under 200 concurrent virtual users, the API shall maintain a failed-request rate below 1%, with read endpoints (e.g. asset list, dashboard summary) at p95 latency under 3000ms and sync submissions at p95 under 5000ms (validated by the k6 smoke test at infra/load/k6-smoke.js).
NFR-SEC-1The API shall refuse to start in production with a missing or weak (<32 char) JWT secret.
NFR-SEC-2All API responses shall be served behind security headers (Helmet) and a global request-rate limiter (default 120 req/60s).
NFR-SEC-3Passwords shall never be stored in plaintext; refresh tokens shall be stored hashed, never in plaintext.
NFR-AVAIL-1Scheduled jobs (maintenance reminders, weekly digest, month-end reports) shall run at fixed UTC times (06:00 daily, Monday 07:00, 1st of month 02:00 respectively) independent of user activity.
NFR-USAB-1All field-facing forms (daily reading, shift report, job card) shall be fully usable with no network connectivity.

§10 Data requirements

The canonical data model is the Prisma schema at apps/api/prisma/schema.prisma (27 models, including Role and RolePermission — see §12). See Technical Details → Data model for the full entity reference including fields and relations.

§11 External interface requirements

InterfaceRequirement
Object storageS3-compatible API (AWS S3 or MinIO) for attachments and generated report files, selectable via STORAGE_DRIVER, with local-disk fallback for development.
Push notificationsFirebase Cloud Messaging HTTP v1 API, authenticated via a Google service account.
EmailSMTP (via nodemailer) for report sharing; logs instead of sending if unconfigured.
API documentationOpenAPI/Swagger UI served at /api/docs with Bearer-token auth.
